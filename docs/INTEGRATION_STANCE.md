# 外部連携スタンス — 「合わせにいく」のではなく「合わせられる余地を残す」

オーナー指示（2026-07-08）:

> ここからあわせるというよりは、合わせられる余地を残しておくようにするのがいいと思う。
> 標準化もしていないから。

配布データセット（`dataset/` + Release バンドル）を、外部プラットフォームや
内部解析群に**今から適合させにいかない**。本プロジェクト自身の標準化がまだであり、
相手の要件を推測で先取りして作り込むのは無駄になる。代わりに、
**後から接続するときに困らない性質**だけを維持する。

---

## 「余地」の具体形 — 既に持っていて、壊さないもの

| 資産 | 役割 | 連携時に効く理由 |
|---|---|---|
| `datapackage.json` | Frictionless Data 記述子（配布物の機械可読カタログ） | 多くのデータポータルが読める共通形式。DCAT 等への変換元になる |
| `MANIFEST.sha256`（zip 同梱＋Release 添付） | 全ファイルのハッシュ台帳 | 提出先がどこでも完全性検証がそのまま通る |
| `CITATION.cff` | 引用メタデータ | DOI 付与型プラットフォーム（IEEE DataPort / Zenodo 等）の必須項目とほぼ1:1 |
| `DATA_DICTIONARY.md` / `DATA_CATALOG.md` | 列・単位・出典の辞書 | 提出フォームの "documentation" 要件に流用可能 |
| 安定 ID（`bus_name`「〜変電所 500kV」・`osm_id`） | レコードの永続識別 | 版間・システム間の突合キーになる |
| CGMES エクスポート（`src/cim/`） | IEC 61970 標準形式 | 電力系統ツール間の相互運用はこちらが担う |
| バージョン規約（`VERSION`＋Release タグ＋zip 名に版番号） | 再現性 | 「どの版を使ったか」を外部が一意に参照できる |

**運用ルール**: 上記を壊す変更（ID の付け替え、記述子の削除、ハッシュ無し配布）は
連携の余地を潰すので、やむを得ない場合は同一コミットで代替手段を用意する。

## 今はやらないこと（観測に留める）

- **IEEE DataPort 等への提出**: 提出先が具体的に決まってから、提出要件を
  一次情報（公式ドキュメント）で確認して着手する。推測で仕様を先取りしない。
- **DCAT / Croissant 等の記述子追加**: 要求するポータルが現れてから
  `datapackage.json` を変換して作る。
- **UC・動的解析（`src/dynamics/`）・AGC との「連携ハブ」化**: 部品は既に
  リポジトリ内にある（UC→潮流注入は `src/uc/pf_injection`、動特性は
  `src/dynamics/`）。配布データセット側から先回りした統合はしない。
  必要になった時点で、その解析が要る入力だけをバンドルに足す。

## 判断の背景

- 本プロジェクトの配布物はまだ v1.4.0 系で形が動く。外部仕様に今ロックすると
  双方の変更に追随するコストだけが残る。
- 2026-07-08 のセッションで、要件を推測で先取りする作業方針が捏造・破綻の
  温床になった実例がある（`docs/reports/2026-07-08_working_with_generative_ai.md`）。
  「相手が確定してから、一次情報で」を原則とする。
