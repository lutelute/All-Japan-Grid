# 発電所DB — ソースと層の設計

**方針（オーナー指示 2026-08-13）**: 「発電機、発電所データベースも作るべき。絶対ある。OSMはしょうがない」

OSM の発電所（plants_all 19,138件）は容量判明率6.7%・大型電源の欠落（柏崎刈羽=issue #37）
という穴がある。OSM に依存せず、**権威データから発電所DBを組む**。

## 調査結果 — 何が公開されているか（2026-08-13）

個別発電所ごとの機械可読な「唯一の権威DB」は、政府側には**無い**。用途別に分かれている:

| ソース | 中身 | 粒度 | 状態 |
|---|---|---|---|
| **OCCTO ユニット別発電実績** | 発電所コード/名前/エリア/燃種 + **実出力30分値** | ユニット単位・486 | ✅ 取得済 |
| **FIT/FIP 事業計画認定情報** | 設備ID/区分/出力/所在地 | 20kW以上の再エネ・数十万件 | ⏳ 取得中 |
| 資源エネ庁 電力調査統計 | 発電所**数**・出力**合計** | 事業者別集計 | 集計値のみ（個別なし） |
| 経産省 発電所一覧 | — | 環境アセス（新設計画）のみ | 既存網羅リストではない |
| e-Stat 発電所認可出力表 | 同上（集計） | 事業者別 | 集計値のみ |
| 国土数値情報 P03 | 発電施設 | 2013年版・名板陳腐化 | enrich で既利用 |
| GEM Global Integrated Power | 発電所・容量 | CC-BY-4.0 | 定格補完の候補 |

→ **大規模電源は OCCTO、再エネは FIT** という二層で組むのが唯一現実的。

## 二層構造

```
大規模電源（原子力・火力・大水力＝系統に直結）
  ← OCCTO ユニット別発電実績（コード・名前・エリア・燃種・実出力）
  ← 定格容量は 供給計画 / GEM で補完（未実装）
  ← 座標は plants_all と名前照合（実装は build_generation_geojson.py に既存）

再エネ設備（20kW以上）
  ← FIT/FIP 認定情報（設備ID・区分・出力・所在地）
  ← 47都道府県別ファイル・月次更新
```

両者は性質が違うので**混ぜず、source列で区別**して1マスタに積む
（`scripts/build_generator_master.py` → `generator_master.csv`、observed層・gitignore下）。

## 何を載せ、何を載せないか

- **載せる**: 施設の客観的事実 — 設備ID・発電所名・区分/燃種・出力・所在地・エリア
- **載せない**: 事業者の**氏名・住所・電話**（FITは個人事業者の個人情報を含む）。
  マスタ化の時点で落とす。生xlsxも gitignore 下に留め再配布しない
- 各レコードに **source（occto_hks / fit_portal）と source_note** を必ず残す（出典必須DB規約）

## 層の位置づけ

すべて **observed層**（docs/OBSERVED_VS_DERIVED.md）。AGJのUC/ディスパッチ計算とは混ぜない。
- OCCTO実績 = その時刻に実際に出た出力（速報値）
- FIT = 認定された設備容量（実際の発電量ではない）

## 取得

```bash
python scripts/fetch_hks.py 2024/04/01 2024/04/07   # OCCTO実績（大規模）
python scripts/fetch_fit.py                          # FIT認定情報（47県・再エネ）
python scripts/build_generator_master.py             # 統合マスタ
```

## 残件

- 定格容量の補完（供給計画 or GEM）— OCCTO実績は定格を持たないため
- FIT設備の座標化（所在地文字列 → 緯度経度のジオコーディング）
- issue #37（柏崎刈羽の欠落）は OCCTO実績側で解消できる
