# 実装・実測メモ

800台UC研究の実装の到達点と、実測の記録。計画は [README](README.md)、実験の作法は [EXPERIMENT_PLAN](EXPERIMENT_PLAN.md)。
ケースはすべて合成800台＋蓄電4台・4地域（`synthetic_case`、seed 17）。実在の個別ユニット台帳ではない。

## 1. 実装済み（10-23〜24、Codex）

- SCIP（PySCIPOpt 6.3 / SCIP 10.0.2）を HiGHS と同じ PuLP モデルから呼ぶ経路。黙って別ソルバーへ落ちない
- ソルバー固有の上界・下界の取得と共通gap `(UB − LB) / max(1, |UB|)`。時間・解数で止まった解も保持
- 窓境界のランプ・起動種別の前史の引き継ぎ、全期間での独立検証器（`src/uc/validation.py`）
- 限界ベンチ（`scripts/uc_limit_benchmark.py`）：1件1プロセス・1スレッド、RSS とwall の監視、打切り理由の区別
- 可視化：[dashboard.html](dashboard.html)（計算資源と到達状態）、[explorer.html](explorer.html)（記録ごとの上下界・検証・規模の試算）

## 2. 60秒での最初の実測（10-24 朝、gpu3060、1スレッド）

| 時間長 | HiGHS | SCIP |
|---|---|---|
| 24h | 検証済みの解、gap 1.46%（探索ノード0、root で時間切れ） | 検証済みの解、下界が負で共通gap 1094% |
| 48h | 解なし（前処理 25 秒、root LP 未了で下界 0） | 解なし（前処理 36 秒） |
| 168h | 前処理中に時間切れ。全体 288 秒のうち HiGHS 本体は約 61 秒 | 8 GiB の RSS 上限で停止 |

60 秒は計画の予算（24/48h は 1 ケース 15 分、168h は 2 時間）よりずっと短い試し打ち。「48h で解けない」はこの予算での話。

## 3. 初期解の受け渡しの修正（10-24 夜、Claude）

### 3.1 HiGHS の初期解は全部拒否されていた

`_HiGHSWarmStart` は、値を持たない列を 0 で埋めた密な解を `setSolution` に渡していた。起動 v・停止 w・起動種別 y が 0 に固定されるため、u に起動が 1 つでもあると矛盾し、HiGHS は「離散変数を固定した LP」が実行不能として初期解を捨てる。

- 40台×48h で確認：`Attempting to find feasible solution by solving LP for user-supplied values of discrete variables` → `Model status : Infeasible`
- ローリング計算が各窓に渡していた前窓の解も、HiGHS では効いていなかったことになる
- 修正：値を持つ列だけを疎な形で渡す。HiGHS は与えた整数（u）を固定して残りを部分MIPで補完する（`solving MIP for user-supplied values of 2112 / 12288 discrete variables`）
- 既存テストは「最適解が出るか」しか見ておらず、初期解が受理されたかは確かめていなかった。受理を確かめるテストを追加（`tests/test_uc_warmstart.py`）

SCIP は PuLP が `createPartialSol` で部分解として渡しており、completesol ヒューリスティックで受理される（40台×48h で 0.1 秒、ローリング解の目的値と一致）。

### 3.2 HiGHS はスレッド数を変えると黙って解かない

HiGHS はプロセスに 1 つのスレッドプールを持つ。同じプロセスで既定のスレッド数で解いた後に `threads=1` を指定すると、`ERROR: Option 'threads' is set to 1 but global scheduler has already been initialized to use 7 threads` で何もせず終わり、PuLP 経由では状態 "Not Set" → 結果は "Not Solved" になる。解く前に `Highs.resetGlobalScheduler(True)` を呼ぶよう修正。同じプロセス内で HiGHS を並行に走らせない前提。

### 3.3 部分MIPの値を上下界の推移に混ぜない

HiGHS は初期解を補完する部分MIPの表を本体の表より先にログへ出す。部分MIPの BestBound は「u を固定した問題」の下界で、元の問題の下界ではない。explorer のログ読み取りではこの区間を推移から外し、補完された初期解の費用だけを「初期解の上界」として拾う。

## 4. ローリング解を初期解にした比較（10-24 夜、gpu3060）

同じ合成ケースを、先に 24h 窓・24h 前進のローリング計算（HiGHS）で解いて全期間を独立検証し、合格した解を全期間一括の MILP に初期解として渡す。ローリングの時間は別に記録し、ソルバーの時間上限は一括の解法だけに掛ける。初期解なしの同条件と比べる。

- 予算：48h は 900 秒、168h は 1800 秒。各 1 スレッド、物理 P コアに 1 本ずつ固定（`taskset`）。同時に最大 6 本
- ローリングの窓：時間上限 300 秒、gap 目標 2%

### 4.1 1 回目は失敗（窓 90 秒・gap 1%）

窓の時間上限を 90 秒にした 1 回目は、初期解ありの 3 本（48h HiGHS・48h SCIP・168h HiGHS）ともローリングが 203 秒で "Not Solved" に終わり、初期解なしと同じ計算になったので止めた（`ws-a13621eb-20261024T1327Z`）。

同じ計算を負荷の軽い状態でやり直すと 2 窓とも成功した。そのときの観測：

- 800×24h は root LP を解き終えるまで解が 1 つも出ない。最初の解は HiGHS の内部時間で 63 秒（Codex の単独計測では 41.6 秒）。6 本同時だと 90 秒の窓に収まらなかったと考えられる
- 窓の HiGHS 上限 90 秒に対して、窓全体は 148 秒。差の約 58 秒は PuLP が HiGHS にモデルを渡す Python 側の処理

ローリング解に要るのは良い実行可能解で、窓ごとの最適性ではない。2 回目は窓の gap 目標を 2% に緩め（root の時点で 1.35〜1.52%）、最初の解が出たら次の窓へ進むようにした。

### 4.2 48h の結果（各 900 秒）

| | 上界（見つけた解） | 下界 | 共通gap | 探索ノード | 全体秒 |
|---|---:|---:|---:|---:|---:|
| HiGHS 初期解なし | 744.44147 億 | 736.18636 億 | 1.109% | 0 | 931 |
| HiGHS ローリング初期解 | 744.44147 億 | 736.25173 億 | 1.100% | 0 | 1,112（うちローリング 175） |
| SCIP 初期解なし | 843.93105 億 | 734.52069 億 | 12.96% | 1 | 915 |
| SCIP ローリング初期解 | 745.26964 億 | 734.62449 億 | 1.43% | 1 | 1,101（うちローリング 171） |

ローリング解（24h 窓 2 つ、窓の gap 1.52%・1.35%）は 745.26964 億で、全期間の独立検証に合格。HiGHS は補完した初期解（745.23539 億）を 1.0 秒、SCIP は 3.4 秒で受理した。

読み取れること：

- **60 秒で「解なし」だった 48h は、計画の予算なら初期解なしでも両 solver で検証済みの解が出る。** 60 秒の結果は予算の問題だった
- **HiGHS は 900 秒たっても root ノードから出ていない。** 律速は解探しではなく下界（root LP とカット）。HiGHS は初期解なしでも約 200 秒でローリング解より良い解を見つけており、初期解の効果はほぼない
- **SCIP には初期解が大きく効く**（共通gap 12.96% → 1.43%）が、SCIP は初期解から改善できていない。SCIP は 1 スレッドで前処理と root LP に 650〜790 秒かかり、探索表の最初の行がそこで出る
- 4 本の上下界を合わせると、この 48h 問題の最適値は **736.25173 億以上 744.44147 億以下**（幅 1.10%）。どの組み合わせでも目標 0.1% には届いていない
- **ローリング解の品質を初めて数字で言える：** 745.26964 億は最適値から多くても (745.26964 − 736.25173) / 745.26964 = **1.21%**

時間の内訳（初期解なし、ソルバーログの時刻）：

| | 前処理 | root LP が解けて表が進み始める | 残りの時間でしていたこと |
|---|---:|---:|---|
| HiGHS | 53 秒 | 285 秒（双対単体法 約 11 万反復、最初の解もここ） | カットの追加を 600 秒。下界 734.50 → 736.19 億（+0.23%） |
| SCIP | 54 秒 | 789 秒（LP 約 26 万反復） | カットを 2 回。下界 734.48 → 734.52 億 |

1 スレッドでは、root LP そのものが重いことと、カットを回しても下界がほとんど上がらないことが律速。

次の一手の候補（[EXPERIMENT_PLAN](EXPERIMENT_PLAN.md) §6「良い UB は早いが LB が停滞」に当たる）：定式化を強めて root の下界を上げる、root LP を並列・別アルゴリズムで速くする（HiGHS の LP は 1 スレッドで数百秒）、週の部分問題から下界を作る。

### 4.3 168h の結果（HiGHS、各 1800 秒）

| | 上界（見つけた解） | 下界 | 全体秒 | 最大 RSS |
|---|---:|---:|---:|---:|
| 初期解なし | なし | 0（自明） | 2,080 | 6.45 GiB |
| ローリング初期解 | 2,448.30864 億 | 0（自明） | 2,591（うちローリング 527） | 6.51 GiB |

- 前処理だけで 435〜447 秒。本体の表が始まるのが約 1,000 秒で、root LP は 1800 秒たっても解き終わらない（双対単体法 31〜37 万反復）
- ローリング（24h 窓 7 つ、窓の gap 1.24〜1.56%）は 527 秒で 2,448.76067 億の解を作り、全期間の独立検証に合格。HiGHS はそれを 3.8 秒で 2,448.30864 億に補完して受理した（部分MIPで u を固定し、出力配分などを最適化し直した分の改善）
- **1 週間の問題では、1 スレッドの単体法では root LP すら 30 分で解けない。** 手元の解はローリング由来のものだけで、品質の保証（下界）は何もない
- SCIP の 168h は、60 秒の試し打ちで 8 GiB を超えたので今回は回していない

ここから言える次の一手：下界を作る手段が要る。候補は (1) ランプ・出力上下限を強い書き方にして LP 下界を上げる、(2) 1 機ごとの分解（動的計画）で下界を作る、(3) 大きな LP を一次法（PDLP、GPU 版あり）で解く。(3) の見込みは [§5](#5-lp-緩和を解く方法の比較) で測る。

## 5. LP 緩和を解く方法の比較

下界が律速なので、下界の出発点である LP 緩和をどれだけ速く解けるかを測った。同じ合成ケース（入力ハッシュを照合済み）の MILP を MPS に書き出し、整数条件を外して解く。

- CPU：pws-gpu3060（i9-12900）、HiGHS 1.14、1 スレッド、presolve あり、時間上限 900 秒
- GPU：共同研究先の GB10、NVIDIA cuOpt 26.10（`cuopt_cli --relaxation`）、CPU 1 スレッド、時間上限 900 秒。許容誤差は既定の相対 1e-4

### 5.1 48h（576,372 行・270,720 変数・非零 2,728,588）

| 解き方 | 計算機 | 時間 | 目的値 |
|---|---|---:|---|
| 双対単体法 | CPU | 107.4 秒 | 734.49632 億（厳密、99,705 反復） |
| 内点法＋crossover | CPU | 322.3 秒 | 734.49632 億 |
| PDLP | CPU | 900 秒で未収束 | — |
| **内点法** | **GPU** | **18.3 秒**（全体 21.4 秒） | 主 734.53 億・双対 734.46 億（相対差 9.8e-5、67 反復） |
| PDLP | GPU | 240.6 秒 | 734.50 億（30 万反復） |

- GPU の内点法は CPU の単体法の約 6 倍速い。計算機の CPU も違うので目安
- PDLP は CPU では収束せず、GPU でようやく実用になるが、この問題では単体法より遅い
- **LP の値そのものは弱いまま。** 最良の解 744.44147 億との差は 1.34%。GPU で速くなるのは下界を得るまでの時間で、差を縮めるには書き方の強化か分解が別に要る
- GPU の値は相対 1e-4 の近似解。下界として使うには、双対解から安全な下界を計算し直す必要がある（このモデルは変数がすべて有界なので可能）

### 5.2 168h（2,021,292 行・947,520 変数・非零 9,941,068）

| 解き方 | 計算機 | 時間 | 目的値 |
|---|---|---:|---|
| 双対単体法（MILP の root、§4.3） | CPU | 1800 秒で未了 | 下界 0 |
| **内点法** | **GPU** | **93.9 秒**（全体 104 秒） | 主 2,413.60 億・双対 2,412.91 億（相対差 2.8e-4、73 反復） |
| PDLP | GPU | 900 秒で未収束 | 途中 2,413.17 億 |

- 実行中の空きメモリは最小 90 GiB（全体 119 GiB）。GB10 は統合メモリで、コンテナのメモリ上限が GPU の確保に効かないので、空き 30 GiB を切ったら止める見張りを付けて回した（`run_lp_guard.sh`）
- **168h のローリング解（2,448.30864 億）は、最適値から多くても約 1.45%**（(2,448.31 − 2,412.91) / 2,448.31）。CPU では 30 分かけても何も言えなかった部分。ただし GPU の近似解からの値で、証明済みの下界ではない。安全な下界の計算し直しは次の課題（変数の上下限が最大 8e3、双対の残差が 1.5e-3 なので、補正は目的値に比べてごく小さい見込み）

### 5.3 ここから言えること

1. GPU の内点法は、48h で CPU 単体法の約 6 倍速く、168h では CPU で解けなかった LP を 94 秒で解く。**LP の下界を得る手段として GPU は効く**
2. ただし LP の下界そのものが弱い（48h で 1.34%、168h で約 1.45%）。目標の 0.1% に向けては、ランプ・出力上下限の書き方の強化や、1 機ごとの分解で下界そのものを上げる必要がある
3. PDLP は CPU では実用にならず、GPU でも内点法に負けた。このモデルでは内点法を優先する

記録：`results/gpu3060/lp-relaxation-20261024/`（CPU）、`results/partner-gb10/lp-relaxation-20261024/`（GPU、環境は `environment.txt`）。

## 6. 下界はどこから漏れているか、どう塞ぐか（10-25）

### 6.1 漏れの内訳

LP 緩和と、最良の解（744.44147 億、HiGHS 48h 初期解なし）の起動停止 u を固定した LP を、同じ MPS から解いて費用ごとに分けた（`scripts/uc_bound_leak.py`、gpu3060・HiGHS 1.14・1 スレッド）。u を固定した LP の値（744.4343 億）は最良の解の費用と一致し、方法が正しいことの確認になる（8 台×24h でも一致）。

| 費用 | LP 緩和 | u 固定 | 差 |
|---|---:|---:|---:|
| 燃料 | 687.428 | 687.449 | +0.020 |
| 無負荷 | 17.602 | 17.577 | −0.026 |
| 停止 | 0.449 | 0.490 | +0.042 |
| 起動（冷） | 22.665 | 37.933 | +15.269 |
| 起動（暖） | 0.000 | 0.798 | +0.798 |
| 起動（温） | 6.352 | 0.188 | −6.165 |
| 計 | 734.496 | 744.434 | +9.938 |

**差 9.94 億の 99.6% が起動の種別。** 今の書き方は「直前 Tw 時間の Σu ≥ 1 なら温起動にしてよい」。LP では u が半端な値（LNG 機で 3,178 機・時間）を取れるので、止めていないのに温起動の条件を満たし、冷起動を安い温起動として数える。

### 6.2 妥当不等式で塞ぐ（`UCParameters.strengthen`）

- `startup_type`：温（暖）起動は、直前 Tw（Tc）時間以内に停止 w があるときだけ。`y_hot ≤ Σw`、`y_hot + y_warm ≤ Σw`。最小運転・停止時間が両方 2 時間以上の機だけに入れる（v と w が同じ時刻に 1 にならないので、今の整数解をすべて満たす）
- `ramp`（対照）：`p_t − p_{t−1} ≤ RU·u_{t−1} + Pmax·v_t` など
- 8 台×24h・3 種で、最適値が変わらないこと、起動の不等式で LP 下界が上がることをテスト（`tests/test_uc_strengthen.py`、gpu3060 で 13 passed）

| 48h の LP 緩和 | 下界 | 最良の解との差 | CPU 1 スレッド |
|---|---:|---:|---:|
| 強化なし | 734.4963 億 | 1.336% | 154 秒 |
| ランプ | 734.5034 億 | 1.335% | 221 秒 |
| **起動の種別** | **738.4986 億** | **0.798%** | 325 秒 |
| 両方 | 738.5118 億 | 0.797% | 350 秒 |

- 起動の種別だけで LP の差の 40% を閉じた。738.50 億は、HiGHS が 900 秒かけた下界（736.25 億）より上。整数解の集合は同じなので、**元の問題の最適値は [738.50, 744.44] 億、幅 0.80%**
- ランプはほぼ効かない（漏れの診断どおり）
- 残る漏れもまだ起動費が中心（LP は温 4.77 億・暖 3.07 億を使う）。w も LP では半端な値を取れるため。次の的
- この書き方で MILP を 900 秒解いた結果は §6.3

### 6.3 強化した書き方での MILP（48h、900 秒、`--strengthen startup_type`）

gpu3060、1 スレッド、物理 P コアに 1 本ずつ、4 本同時。`results/gpu3060/strengthen-20261025/`。

| | 上界 | 下界 | 共通gap | 探索ノード |
|---|---:|---:|---:|---:|
| HiGHS 初期解なし | 743.8546 億 | 739.6119 億 | 0.570% | 0 |
| HiGHS ローリング初期解 | 743.8546 億 | 739.6495 億 | 0.565% | 0 |
| SCIP 初期解なし | 848.3997 億 | 負（root 未了） | 1119% | 1 |
| SCIP ローリング初期解 | 745.2696 億 | 負（root 未了） | 1260% | 1 |

- **HiGHS の gap は 1.11% → 0.57%（ほぼ半分）。** 下界が上がっただけでなく、見つかる解も 744.44 → 743.85 億と、これまでで最良
- 合わせると、**最適値は [739.65, 743.85] 億、幅 0.565%**（§4.2 の [736.25, 744.44]、幅 1.10% から）
- **SCIP は悪化。** 式が増えて root の LP が重くなり、900 秒で root を終えられなかった。SCIP で使うには、不等式を最初から全部入れず、破られたものだけを足す（カットとして分離する）形が要る
- HiGHS は今回も探索ノード 0（root のまま）。残りの幅も、まず下界の側（残る起動費の漏れ）

### 6.5 初期状態（「全機停止から」のくせを外す）

合成ケースは全機が 12 時間以上止まっていた状態から始まるので、0 時に動かす機はすべて冷起動になる。同じ 24〜71 時の 48 時間を、全機停止から（R1）と、48h の最良の解の 23 時の状態（運転の有無・続けた時間・出力・蓄電の残量）から（R2）の 2 通りで解いた。HiGHS・起動の不等式あり・900 秒・1 スレッド。`results/gpu3060/initial-state-20261025/`、`--start-hour 24 --initial-state ... --initial-state-hour 23`。

| | 上界 | 下界 | gap | 0 時に運転 | 0 時以降の起動 | 起動費 |
|---|---:|---:|---:|---:|---:|---:|
| R1 全機停止から | 750.88 億 | 747.44 億 | 0.458% | 447 台 | 362 回 | 37.39 億 |
| R2 動いている状態から | 727.31 億 | 724.74 億 | 0.352% | 450 台 | 336 回 | 12.37 億 |

- 費用の差 23.6 億は、ほぼ 0 時の一斉冷起動の分（起動費の差 25.0 億）。0〜47 時の解でも 0 時の冷起動は 22.94 億だった
- gap も小さくなる（0.46% → 0.35%）。実際の運用に近い始め方のほうが、少し解きやすい

### 6.6 段階的に解く（全国 → 地域、オーナーの発意）

### 6.7 1 週間（168h）を強化した書き方で

ローリングの初期解つき、HiGHS 1800 秒（`results/gpu3060/strengthen-20261025/t168/`）：上界 2,448.31 億、下界 0。起動の不等式を足しても、CPU 1 スレッドでは 1 週間の根の LP が 30 分で解けない。1 週間の下界は GPU の内点法だけが出せる。強化した LP は gpu3060 の CPU 内点法では 1 時間で終わらず（57 反復）、共同研究先の GB10 は GPU が見えなくなっていた（`no CUDA-capable device`、ホスト側でのコンテナの再起動が要る）ので、PGX の sgnb（GB10）で解いた（`results/pgx-gb10/lp-relaxation-20261025/`）

### 6.16 再給電 LP を順に解く形に直して、1 年を回し直す（10-25）

6.15 の再給電 LP は罰金 1 本で、双対（1 MW の価値）が罰金に引っ張られていた。`scripts/scuc_redispatch.redispatch_lp` を同じモデルの解き直しで順に解く形にした：①あふれの合計を最小（同じなら元からあふれていた線に残す：重み 1 と 1.001）②その量のまま燃料費を最小 ③線ごとのあふれを②の値で固定 ④効いている線を 1 本ずつ 1 MW 広げて解き直し、下がった燃料費をその線の 1 MW の価値とする。3 母線の検算 4 本（`tests/test_scuc_redispatch.py`）。

途中で踏んだもの（どれも 1 年分を回す前に見つけた）:

- **あふれの予算の遊びは燃料に使われる**：①の最小値に 0.01 MW の遊びを持たせたら、②がそれを使って安い機へ寄せ、あふれていない線が「あふれ 0.01 MW」になった → 遊びは 1e-7 相対、0.05 MW 未満は「消えた」と数える
- **LP があふれを別の線へ押し付ける**：越後〜新潟は前 2,385 時間・後 4,360 時間（後のほうが多い）。合計が同じなら押し付けても損がないため → ①に重み、数えるのは「前にあふれ、同じ時刻に後も残った」時間（`hours_stuck`）
- **双対だけでは 1 MW の価値を言いすぎる**：線にほとんど効かない機（PTDF 1e-4 程度）しか動かせない線では、双対が「燃料の差 ÷ 感度」になり 1 時間で 1.3 億円/MW（洛南〜北大阪 275kV、fy2023r2）。1 MW 分を動かす前に機の上限に当たるので、④で実際に解き直して測る（検算：双対 5,000、実測 400）
- **HiGHS の warm start が「状態不明」で止まる**：東 fy2023r2 の 0 時で③が、別の条件で④の 4 回中 3 回が kUnknown。④の失敗は黙って価値 0 になっていた → 失敗したら解き直し（cold）→ 内点法。失敗は数えて残す
