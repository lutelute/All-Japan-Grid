# 実験計画と継続判断

状態: 未実行の計画。対応する[experiment_matrix.yaml](experiment_matrix.yaml)は将来のrunner用の仕様案であり、現在のCLIへ渡す設定ファイルではない。

## 1. 先に比較の単位を揃える

最初の比較は「同じ正準問題・同じMPS・同じ目的・同じ許容差」をHiGHSとSCIPへ渡す。これによりsolver差を測る。次の比較で定式化を変え、整数実行可能集合と費用の等価性を確認してからformulation差を測る。補完・容量・予備力条件を同時に変えない。

公開外部ケースには[UnitCommitment.jlの問題定義・ベンチマーク](https://anl-ceeesa.github.io/UnitCommitment.jl/0.4/guides/problem/)を利用候補とする。バージョン・元データ出典・利用条件を固定し、対応しない制約を明示する。モデル意味が違うまま結果だけを比べない。

## 2. ケース群

| 群 | 規模 | 目的 |
|---|---|---|
| C0 | 4〜10台、24〜72h | 状態・費用・分解LBの正しさ。列挙可能な極小例も含む |
| C1 | 100/400/800台、24/48/168h | 定式化・backend・初期解の切り分け |
| C2 | 800台、720h | rootメモリ、長期資源、分解境界の試験 |
| C3 | 800台、全暦時系列 | 連続な年間UB、年間LB、gap、終端条件の影響 |
| C4 | 公開外部SCUCケース | 日本データだけに効く調整になっていないかの検証 |

実データ系と合成系を別ディレクトリ・別instance IDにする。100/400台は適切に需要・連系容量等を設計した規模実験であり、800台実系統の忠実な縮小とは呼ばない。

日間・週間は季節・高低需要・高低再エネ・夕方ランプ・連系線混雑・定検集中・低再エネの連続期間を含める。調整用と評価用は時間の離れた週で分離し、重複したrolling窓を両方へ入れない。800台を固定した難度系列も用意し、意図的にinfeasibleなケースは性能集計と診断評価を分ける。

## 3. 比較する方法

| ID | 手法 | 比較で答える問い |
|---|---|---|
| B0 | 監査・修正後の既存モデル＋HiGHS | 現行資産からどれだけ改善したか |
| B1 | 同じMPS＋SCIP単体 | backendだけの違いは何か |
| B2 | 等価な強化UC定式化＋SCIP単体 | root LP、構築時間、node数のどこに効くか |
| P1 | B2＋SCIP concurrent mode | 設定を変えた同一問題並列の効果はあるか |
| P2 | B2＋FiberSCIP | 共有メモリの探索並列が効くか |
| P3 | B2＋ParaSCIP | 分散メモリの探索並列が効くか |
| H1 | B2＋固定/ランダム近傍 | 専用近傍を評価するための対照 |
| H2 | B2＋イベントをまたぐ近傍 | 同じ予算で初期解・UB改善が速いか |
| Y0 | 境界を正しく引継ぐrolling、48/72/168h先読み | 年間UBと先読み効果の基準 |
| Y1 | Y0＋境界修復＋週Lagrangian LB | 年間gapをどこまで閉じられるか |
| Y2 | Y1＋適応的ブロック長/資源配分 | 固定分解・固定資源配分に勝つか |
| Y3 | 列生成/GCG等の代替 | Y1の下界が停滞する場合に追加する |

P1とP2は同じものではない。[SCIP concurrent mode](https://scipopt.org/doc/html/CONCSCIP.php)は複数の設定で同一問題を並行して解く仕組み。FiberSCIP/ParaSCIPの比較ではUGの版・通信設定を記録する。

## 4. 計算資源と仮目標

候補資源は、開発用の単一ノード、32〜64 physical coreの共有メモリ環境、複数ノードの128〜256 coreからのMPI実験。**所有・利用許可・容量は未確認**。1ワーカー当たりメモリを実測し、MPI数×モデル複製＋通信・管理分＋余裕がノードメモリに収まる範囲で開始する。

| 問題 | 仮の品質目標 | 仮の時間予算 | 判断 |
|---|---|---|---|
| 800台24/48h・Z | gap≤0.1%、全制約PASS | 1ケース15分、単一ノード | まず3 seedで分布を把握。未達ならroot/探索/構築を切り分け |
| 800台168h・Z | gap≤0.5%、全制約PASS | 1ケース2時間、単一ノード | 並列化と定式化の双方を比較 |
| 年間UB・Z | 全時刻・境界PASS | 24時間を初期上限 | LBがなくても実行可能性の成果として報告 |
| 年間UB/LB・Z | 有限LB、その後gap≤1% | 調整・検証を含む72時間を初期上限 | 未達gapと資源を公表。0%は段階的な追加目標 |

数字は実測後に改訂する研究用の予算案。HPC確保・ジョブ投入を承認したものではない。たとえば256 coreを72h占有すると18,432 allocated core-hourとなるため、小実験の選別後に限定して実施する。

## 5. 記録・公平性

- full pipeline時間とsolver時間を両方測る。MPS作成・読込・presolve・root・探索・通信・検証・年間調整を含める。
- 解到達時間、UB/LB曲線、gap、primal/dual integral、peak RSS、失敗・OOM・time limitを保存する。解がない区間のintegral規約を固定する。
- strong scalingは同じ問題・同じ終了品質で1/2/4/8/16/32/64 worker等を比較する。資源競合がなく、memory内に収まる組だけ実行する。
- 同じcore-hourの「一つのParaSCIP」と「複数の独立SCIP/週部分問題」も比較する。二重の並列化でoversubscriptionしない。
- 段階選別中は3 seed、最終候補は5 seedを基本案とする。並列の再現性は設定・ビルドとともに記録する。
- 時間制限に達したケースを落とさず、solved率・分位点・打切り件数を報告する。成功例だけの速度比を平均しない。
- checkpointからの再開は解の継続と証明情報の継続を区別する。保存したLBは同一問題か検査してから再利用する。

## 6. 結果ごとの次の一手

| 観測 | 次の実験 |
|---|---|
| モデル構築・root LPで大半を消費 | 変数/制約/非零数・Pythonオブジェクトメモリ、不要なbinary、係数スケール、定式化のcompactness、LP solverを評価 |
| 初期解が遅い | rolling解の投入、修復MILP、イベント近傍。候補は元問題で検証 |
| 良いUBは早いがLBが停滞 | 強い定式化、cut、部分問題LB、ブロック長、必要なら列生成 |
| ParaSCIPのwall timeは改善するがcore-hourが悪化 | interactiveな期限が必要な問題に用途を限定し、年間では独立部分問題へ資源を回す |
| 境界の修復が繰り返し失敗 | 履歴・資源・終端方針を点検し、窓を広げる。実行不能な連結解をUBにしない |
| 数学的gapは小さいが実測と乖離 | データの年代・燃料費・稼働状態・需要・容量補完を監査。solver改善とモデル校正を別の実験にする |
